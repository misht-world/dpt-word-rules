# Контекст проекта для Claude Code

Этот проект вырос из чата с Claude (веб/десктоп), где мы вместе:
1. Обсудили и согласовали список типографских правил для .docx-документов
   Михаила (урбанистика, ДПТ/ППТ, справки, юридические документы).
2. Написали `rules.py` (правила) и `apply_docx.py` (применение к .docx) —
   типографика: неразрывные пробелы, дефисы, единицы измерения.
3. Протестировали на 4 реальных документах пользователя (~800KB–1.3MB,
   933–2500+ абзацев каждый), нашли и исправили около десятка ложных
   срабатываний на реальном тексте.
4. Отдельно занялись структурной нормализацией: стили, списки, таблицы,
   поля страницы, заголовки — `normalize_structure.py` + `style_injector.py`.
   Это другая по природе задача: не текст, а форматирование/структура
   документа. Включая самую сложную часть — единую автонумерацию
   заголовков на весь документ.

Полная информация:
- **README.md** — типографика (`rules.py`/`apply_docx.py`): как пользоваться,
  список правил, известные ограничения.
- **FORMATTING_SPEC.md** — структурная нормализация
  (`normalize_structure.py`/`style_injector.py`): что реализовано, что нет,
  технические детали, как устроена единая нумерация заголовков.
- Этот файл (**CLAUDE.md**) — архитектурные решения обоих пайплайнов,
  которые не стоит переизобретать, и типичные грабли.

## Статус на момент последней передачи в Claude Code

**Пайплайн типографики** (`rules.py`/`apply_docx.py`) — рабочий и
проверенный на 4 документах, полностью самодостаточный (нет внешних
зависимостей кроме `lxml`).

**Пайплайн структуры** (`normalize_structure.py`/`style_injector.py`) —
полный рабочий пайплайн, включая заголовки, проверенный на тех же 4
документах (прогонялось, результат конвертировался в PDF, смотрели глазами
— структура/списки/таблицы/заголовки/поля страницы не ломаются). Делает:
вклеивает провалидированные стили «ДПТ - …», переводит обычный текст в
«ДПТ - Основной», конвертирует вручную напечатанные списки (`- текст` и
`1) текст`) в настоящие Word-списки, переоформляет таблицы, применяет поля
страницы (только к книжным секциям), и **переводит АБСОЛЮТНО ВСЕ заголовки
документа на единую схему автонумерации** (`DPTHeading1..5`) — подробно
см. FORMATTING_SPEC.md → «Заголовки: как это работает и почему именно так».

## Как тестировать изменения

### Типографика
1. `python test_samples.py` — быстрая проверка на изолированных строках.
2. `python apply_docx.py документ.docx --dry-run --report report.txt` —
   отчёт по реальному документу перед применением.

### Структура
1. `python normalize_structure.py документ.docx выходной.docx --report report.txt`
   — прогоняет и сразу пишет отчёт (нет отдельного `--dry-run` пути без
   записи файла — можно сделать, но пока не сделано, TODO при желании).
2. Визуальная проверка — обязательна для структурных изменений сильнее, чем
   для типографики (тут риск сломать таблицы/списки/оглавление/нумерацию
   заголовков выше): сконвертировать результат в PDF (LibreOffice headless)
   и посмотреть несколько страниц, особенно там, где были заголовки разных
   уровней подряд — самое уязвимое место (можно случайно сбить вложенность).
3. `make_demo.js` (`node make_demo.js`, нужен npm-пакет `docx`) — генерирует
   `demo_formatting.docx`, живой пример всех стилей (5 уровней заголовков,
   оба вида списков, таблица). Если меняется `style_spec.json` (шрифты/
   отступы/формат номеров/число уровней), стоит перегенерировать demo и
   визуально свериться, ПОТОМ уже заново извлекать
   `dpt_styles_fragment.xml`/`dpt_numbering_fragment.xml` (это ручной
   процесс, не автоматизирован — см. ниже алгоритм).

## Важные архитектурные решения — типографика (rules.py/apply_docx.py)

- **Правила работают на уровне текста абзаца**, а не отдельных `<w:r>`,
  потому что Word произвольно дробит текст на run'ы — работать с одним
  run'ом ненадёжно.
- **Изменения возвращаются в run'ы через `difflib.SequenceMatcher`**
  (см. `redistribute()` в apply_docx.py) — не теряет форматирование
  (жирный/курсив/цвет) внутри абзаца при точечных правках текста.
- **Порядок правил в PIPELINE важен.** Общие правила (`fix_prepositions`,
  `fix_dashes`) идут последними, чтобы не перехватывать то, что должно
  обработать более специфичное правило раньше.
- **Идентификаторы (шифры, номера документов) защищаются от диапазонов**
  через отдельные правила, выполняющиеся раньше `fix_dashes` в конвейере.
- **`_sub()` в rules.py логирует в глобальный список `LOG`.** Важно:
  `apply_all(text, log=True)` каждый раз ПЕРЕСОЗДАЁТ список `LOG` — при
  прямом `from rules import LOG` ссылка станет устаревшей. Правильно —
  `import rules as R`, читать `R.LOG`.

### Известный нерешённый погранслучай (типографика)

Правило `em-dash` иногда путает тире-знак-препинания с опечаткой
«слово - слово» вместо «слово-слово» (лишние пробелы вокруг дефиса сложного
прилагательного в исходнике, напр. «общественно - деловой»). Редкий случай
(единично на большой документ) — оставлено как есть, видно в dry-run отчёте.

## Важные архитектурные решения — структура (normalize_structure.py/style_injector.py)

- **Стили не пишутся в Python с нуля — извлекаются из реального Word-файла.**
  `make_demo.js` (docx/npm) генерирует `demo_formatting.docx`, визуально
  проверенный в Word; из его `word/styles.xml`/`word/numbering.xml`
  извлечены `dpt_styles_fragment.xml`/`dpt_numbering_fragment.xml` — именно
  их вклеивает `style_injector.py` в целевые документы. Причина: OOXML для
  многоуровневой автонумерации/стилей — с тонкостями, легко разойтись с тем,
  что реально поддерживает Word, если писать логику заново.
- **Найденный и исправленный баг генератора:** `docx` (npm) при комбинации
  `numbering` + `paragraphStyles` подмешивал лишний
  `<w:pStyle w:val="ListParagraph"/>` внутрь `pPr` самого стиля — невалидная
  вложенность (стиль не должен ссылаться на другой стиль изнутри своего же
  `pPr`, для этого есть `basedOn`). Убран вручную при извлечении фрагмента.
  **Если `dpt_styles_fragment.xml` придётся перегенерировать заново из
  `make_demo.js` — обязательно проверить**: `grep ListParagraph
  dpt_styles_fragment.xml` должен ничего не находить, иначе повторится
  путаница «почему в Word вместо моего стиля показывается Абзац списка».
- **Инъекция стилей идемпотентна и учитывает существующую нумерацию**
  целевого документа — `style_injector.inject()` сдвигает
  `abstractNumId`/`numId` на основе максимума уже существующих в документе,
  чтобы не столкнуться. Все 4 документа пользователя уже содержат
  `word/numbering.xml` — случай полного отсутствия этой части не
  реализован.
- **Именование стилей — «ДПТ - …»**, не случайное: это существующая в
  эталонном документе конвенция (там уже были «ДПТ - Основной», «маркер»).
  Смысл: если в целевом документе стиль с таким именем уже есть (даже с
  другим оформлением) — переопределение каскадируется на весь текст, уже
  им помеченный, без правки document.xml.
- **Списки детектируются по литеральному тексту** — `^-[ \t\u00A0]+` для
  маркированных, `^\d+\)[ \t\u00A0]+` для нумерованных. Эти форматы
  гарантированно не путаются с форматом заголовков (`N.`, `N.N.` — точка и
  вложенность против `N)` — скобка, один уровень). Маркер вырезается через
  `_strip_leading()` (может быть размазан по нескольким `<w:r>` — обрезает
  последовательно).
- **Прямое форматирование намеренно убирается** при переприсвоении стиля —
  это и есть источник визуального разнобоя между документами. Для обычного
  текста (`clear_conflicting_ppr`/`clear_conflicting_rpr_fonts`) сохраняются
  bold/italic/underline (часто осмысленное локальное выделение). Для
  заголовков (`clear_heading_run_formatting`) убирается ВСЁ форматирование
  run'ов без исключений — заголовок должен целиком определяться стилем.
- **Таблицы отличаются от layout-обёрток по числу столбцов** —
  `is_real_data_table()` проверяет `tblGrid`/реальное число `tc` в строках
  (>1 столбец = настоящая таблица с данными).
- **Поля страницы применяются только к книжным (portrait) секциям.**
  Альбомные (landscape) — пропускаются осознанно: в реальных документах
  landscape используется под широкие таблицы (в одном документе оказалось
  23 секции, 11 landscape), и портретная спецификация полей для них не
  подходит без отдельного решения.

### Заголовки — единая нумерация (решено, не откладывать назад к "не трогать")

**Это была самая сложная часть проекта, решённая в несколько итераций.**
Полная история и обоснование — в FORMATTING_SPEC.md, здесь — только то, что
нельзя откатывать назад по незнанию:

- **НЕ пытаться "защищать" уже стилизованные заголовки от переприсвоения.**
  Ранняя версия кода так делала (пропускала абзацы с существующим
  outline-стилем) — это ОШИБКА, а не более безопасный вариант. Причина:
  родная нумерация документов устроена индивидуально и ненадёжно (цепочки
  `w:numStyleLink` и т.п.), и если оставить часть заголовков на родной
  нумерации, а "сломанные" (без стиля) перевести на нашу — в документе
  останется смесь двух несогласованных систем нумерации. Правильно —
  переводить АБСОЛЮТНО ВСЕ заголовки на `DPTHeading1..5`, без исключений.
- **`resolve_outline_level()` разворачивает ПОЛНУЮ цепочку `basedOn`**, а не
  проверяет `outlineLvl` только в самом стиле абзаца — в реальных
  документах `outlineLvl` часто наследуется от базового стиля через
  несколько звеньев. Прямая проверка (`if outlineLvl in style: ...`) —
  найденный и исправленный баг ранней версии, из-за которого часть
  верхнеуровневых заголовков не распознавалась.
- **Детектор "сломанных" заголовков** (`classify_heading_text()`) —
  регулярка на номер в начале строки + несколько фильтров, найденных
  тестированием на реальных данных (год-подобные 4-значные сегменты,
  слишком длинный текст, конец обычного предложения, локальные подсписки
  вида "1. Текст:" с одноуровневым номером). Результат: 10/10 верно,
  0 ложных срабатываний на 4 документах. Если будете расширять фильтры —
  прогонять на всех 4 исходных документах и сверять эти числа.
- **`MAX_HEADING_LEVEL = 5`** должен совпадать с числом уровней в
  `dpt_styles_fragment.xml`/`dpt_numbering_fragment.xml`. Расширение
  уровней требует перегенерации demo и повторного извлечения фрагментов.

## Ключевые числа для калибровки регрессионных тестов

**Типографика:** на 4 исходных документах правило `preposition` — самое
частое (тысячи срабатываний, это нормально). Остальные правила
единичные/десятки — резкий скачок на порядок у специфичного правила
(`project-code`, `org-name`, `city-g`, `range-dash`, `em-dash`,
`normdoc-ref` и т.п.) обычно значит новое ложное срабатывание.

**Структура (после внедрения единой нумерации заголовков):**
- Пояснительная записка: 517 обычный текст, 12 маркированных списков,
  9 таблиц, 56 заголовков из стиля + 10 заголовков из текста (все L3), 1
  секция.
- Положение: 55/0/3/1 заголовок из стиля/0/1 секция.
- Том_2: 42/0/5/2 заголовка из стиля/0/1 секция.
- Том_3: 1058 обычный текст, 4 нумерованных списка, 73 таблицы, 138
  заголовков из стиля, 0 из текста, 23 секции (12 portrait обработано, 11
  landscape пропущено).

Если эти числа резко меняются после правок кода — вероятно, регрессия,
стоит разобраться через отчёт (`--report`) и визуальную проверку в PDF,
особенно смотреть на последовательность номеров заголовков разных уровней
подряд (например, переход `13.` → `13.1.` → `13.1.1./13.1.2.` должен быть
непрерывным без скачков или дублей).
