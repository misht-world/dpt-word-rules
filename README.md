# dpt_word_rules — типографское оформление .docx

Скрипт расставляет неразрывные пробелы/дефисы, унифицирует единицы измерения,
приводит кавычки к «ёлочкам» и т. д. по правилам, согласованным под
градостроительную/юридическую документацию (ДПТ/ППТ, справки, договоры,
пояснительные записки).

## Установка

```
pip install lxml
```

## Использование

```
python apply_docx.py входной.docx выходной.docx --report отчёт.txt
```

Только посмотреть, что изменится, без записи файла:
```
python apply_docx.py входной.docx --dry-run --report отчёт.txt
```

## Структура проекта

- `rules.py` — все текстовые правила (чистые функции text -> text), собраны
  в список `PIPELINE` в конце файла. Правила независимы друг от друга,
  порядок в `PIPELINE` важен (специфичные правила — раньше общих, диапазоны
  чисел/идентификаторы — до общего правила тире).
- `apply_docx.py` — CLI-обвязка: распаковывает .docx, сливает соседние
  одинаково отформатированные `<w:r>` (чтобы текст не был разбит на куски),
  для каждого абзаца прогоняет `rules.apply_all()`, аккуратно распределяет
  изменения обратно по исходным run'ам через `difflib` (не ломает жирный/
  курсив внутри абзаца), добавляет `keepNext` абзацам, оканчивающимся на «:»
  (чтобы заголовок списка не отрывался от первого пункта), запаковывает
  обратно в .docx.
- `test_samples.py` — быстрый прогон правил на изолированных строках-примерах
  (без .docx, просто текст → текст). Запуск: `python test_samples.py`.

## Как проверить правило на реальном документе (dry-run + отчёт)

```
python apply_docx.py "мой_документ.docx" --dry-run --report report.txt
```
В `report.txt` — каждый изменённый абзац: было/стало + список сработавших
правил с указанием старого и нового фрагмента. Полезно для вычитки перед
тем, как принимать правки на юридических документах.

## Полный список правил (сводка)

**Неразрывные пробелы:**
предлоги/союзы (1–2 буквы) + следующее слово; инициалы + фамилия; число +
единица измерения; «т. д. / т. е. / т. п. / и др. / в т. ч.»; № (до и после);
ст./ч./п. ГрК РФ; СП/ГОСТ/РМД/СанПиН/СНиП/РД + номер; ул./пр./пер./наб./пл./
ш./б-р (сторона определяется по заглавной букве соседнего слова; «и пр.»
распознаётся отдельно и не путается с «проспект»); д./кв./корп./лит. + номер;
ЗУ/ОЗУ/ОКС/лист + номер; исх./вх. + номер; организационно-правовая форма
(ГУП/ООО/АО/ОАО/ЗАО/ПАО/ИП/...) + «Название» (весь пробел внутри кавычек
тоже неразрывный); ППТ ЛО / ПЗЗ СПб / ГП СПб; «г.» (год или город —
определяется по контексту: число перед → год, заглавная буква после →
город); «ст. NNN в.д.» (сталь высокого давления).

**Единицы измерения:** м²/м2/м³/m3 → «кв. м» / «куб. м»; мм, см, км, га, %,
руб., °C, л/с, кВт, кВА, кВ, чел., Гкал/ч, т/сут — с неразрывным пробелом
перед единицей.

**Дефисы/тире:** короткое тире в диапазонах чисел («2020–2026»); длинное
тире как знак препинания (со стороны и после — обычный пробел, перед —
неразрывный); неразрывный дефис в «Санкт-Петербурге», в шифрах проектов
(«ДПТ‑2025/01»), в номерах документов и регистрационных номерах со слэшами
(«78‑78/006‑78/006/001/2015‑412/1»).

**Кавычки:** прямые `"..."` → «ёлочки».

**Структура абзаца:** абзац, оканчивающийся на «:», получает `keepNext` —
держится на одной странице с первым пунктом следующего списка.

## Известные ограничения

- Правило «длинное тире» иногда путает тире-знак-препинания с опечаткой вида
  «слово - слово» вместо «слово-слово» (когда в исходнике по ошибке стоят
  пробелы вокруг дефиса сложного прилагательного, например
  «общественно - деловой» вместо «общественно-деловой»). Такие места стоит
  проверять по отчёту — в реальных документах встречается редко (единичные
  случаи на весь документ).
- «пр.» как «проспект» отличается от «и пр.» (и прочее) только по наличию
  предшествующего «и» — более сложные конструкции не разбираются.
- Организационно-правовые формы (`FORMS` в rules.py) — список фиксирован;
  если встретится новая форма (например, СПб ГУП, ФГУП) — добавить в regex.

## Куда добавлять новые правила

Правила в `rules.py` — независимые функции `text -> text`. Чтобы добавить
новое:
1. Написать функцию `fix_XXX(text)`, использующую `_sub(pattern, repl, text,
   'имя-правила')` для автоматического логирования в отчёт.
2. Добавить её в список `PIPELINE` в нужном месте (более специфичные
   правила — раньше общих типа `fix_prepositions` и `fix_dashes`, которые
   должны идти последними).
3. Проверить на `test_samples.py` и на dry-run реальных документов —
   особенно посмотреть, не перехватывает ли новое правило то, что раньше
   обрабатывалось другим (или наоборот).
